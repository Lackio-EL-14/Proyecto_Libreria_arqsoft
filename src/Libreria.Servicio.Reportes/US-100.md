## Funcionamiento y filtros

ProductReportRepository une Producto, Categoria y Marca por las claves existentes.
Selecciona nombre, precio, categoría y marca, exclusivamente de productos activos,
ordenados por nombre y PublicId para desempatar. No impone el límite de diez filas
del ejemplo US-99 ni consulta Usuarios. El selector ofrece categorías activas,
como el catálogo existente; no se cambian las reglas de estado de otros módulos.

Los tres valores opcionales son CategoryPublicId (GUID), MinimumPrice y MaximumPrice.
Sin valores se consultan todos los productos activos; los límites son inclusivos y
pueden usarse por separado o combinados con la categoría. Todo se envía mediante
parámetros ADO.NET, incluyendo los valores nulos. No hay cambios de esquema o datos.
Se rechazan precios negativos, mínimo mayor que máximo, GUID vacío y entradas que
no puedan convertirse a GUID/decimal. La validación existe en Front y servicio.

ReadProductReportUseCase valida y arma el documento con el usuario del encabezado
y la fecha UTC. ReporteFacade elige el creador PDF o Excel existente. Los generadores
ahora admiten categoría y marca en el reporte de productos; el ejemplo US-99 mantiene
sus dos columnas y su gráfico. La lista de US-100 no necesita gráfico.

ServicioReportesClient usa el HttpClient ya registrado y conserva el handler de
identidad. Las consultas JSON reutilizan ApiClientBase; la descarga binaria se
resuelve dentro del cliente de Reportes porque la base compartida solo acepta JSON.
El Front posee DTOs propios y no referencia ningún proyecto de servicio.

Rutas nuevas:

- GET `api/reportes/categorias`.
- GET `api/reportes/productos?CategoryPublicId=<guid>&MinimumPrice=10&MaximumPrice=50`.
- GET `api/reportes/productos/exportar?format=Pdf&MinimumPrice=10&MaximumPrice=50`.
- La última ruta acepta `format=Excel` y los mismos filtros.

La página utiliza `Filter.CategoryPublicId`, `Filter.MinimumPrice` y
`Filter.MaximumPrice`; el cliente los transforma en parámetros de la API con
decimales de cultura invariante. Los dos botones conservan los valores actuales
del formulario. Los errores y resultados vacíos se muestran en español.

## Prueba manual y defensa

1. Tener SQL Server accesible con las tablas/datos existentes y configurar
   `ConnectionStrings__LibreriaDb` para Reportes. No guardar la cadena en Git.
2. Iniciar Usuarios (para login), Reportes y el Front en terminales separadas:

```powershell
dotnet run --project src/Libreria.Servicio.Usuarios --launch-profile http
dotnet run --project src/Libreria.Servicio.Reportes --launch-profile http
dotnet run --project src/Libreria.Client --launch-profile Libreria.Client
```

3. Entrar al Front con un Administrador y abrir Reportes desde el menú o `/Reportes`.
4. Consultar sin filtros, después por categoría, por precio y combinando ambos.
   Comprobar el orden alfabético y las cuatro columnas.
5. Pulsar Descargar PDF y Descargar Excel. Abrir ambos y comprobar que respetan los
   filtros, contienen el usuario generador y la fecha/hora UTC.
6. Probar un rango sin coincidencias y mínimo mayor que máximo: debe aparecer el
   mensaje correspondiente. Se pueden probar directamente los endpoints con el .http.

Para la defensa: el Front solo llama HTTP; el caso de uso valida y consulta mediante
una interfaz; el repositorio hace SELECT con JOIN y parámetros; ReporteFacade usa
los creadores existentes para producir el PDF/Excel del mismo documento. La
plantilla futura se aplicará en los generadores, sin modificar los filtros ni SQL.
